The knob the experiment actually moves — TLP's CPU_MAX_PERF_ON_AC and
intel_pstate's no_turbo — is unchanged across that boundary, which is why the
comparison still holds. The kernel is not: it moved four patch releases four
days after the runs. Read the frequency and power numbers, including the
283,300 throttle events, as belonging to 6.12.107.

The since-boot throttle counters above are a *baseline for the next run*, not
evidence about these ones — they reset at boot, and 0/0 means this boot has not
throttled yet. The evidence for each run is its own delta, recorded per row in
results.csv (column `throttle_delta`) and read from the MSR-backed
/sys/devices/system/cpu/cpu*/thermal_throttle/*_count files before and after the
load, so a run cannot inherit another run's events.

what produced the numbers
-------------------------
    sudo ./run-ci-loads.sh                                          # real pnpm test at both caps
    sudo ./experiment.sh C2_fft_2400mhz_static 71 1 420 raw          # 2.4 GHz, turbo off
    sudo ./experiment.sh T3_fft_turbo_3400mhz  100 0 420 raw         # 3.4 GHz turbo, the cliff
    sudo ./experiment.sh D_partialturbo_2720mhz 80 0 425 raw         # 2.72 GHz, no clamp, no margin
    sudo ./experiment.sh A_ktrip60_2400mhz 71 1 95 ktrip             # kernel passive trip @60 C
    sudo ./experiment.sh B_guard_turbo_3400mhz 100 0 185 guard       # userspace guard under turbo

Every run waits for the package to fall to <= 56 C before it starts. That gate
exists because the previous round of measurements did not have it, and the
missing gate — not the CPU — is what produced the conclusion this one overturns.

Frequency comes from turbostat's Bzy_MHz. `scaling_cur_freq` cannot be used in
intel_pstate passive mode: it reports a target that sits near 1297 MHz whatever
the core is doing, so it is blind to the 800 MHz clamp.
